# M4.3 · The level editor, II: the rules, a solvability check and sharing: spec

The spec for M4.3 (`docs/M4/M4.md` has the plan and the decisions this builds on; `docs/M4/M4.2.md` is the editor
it extends). It's for the designer to approve before anything is built. **Nothing in it is built yet.**

*(Designer, 2026-10-07)*: the editor's levels can be exported and shared; **a shared level carries its author's
solution**, offered after three failed runs (QA-042); the author must solve it in test-play before sharing.
**The engine is the only judge.** One YAML format.

**Branch:** `m4-3-editor-rules`, from `main` (M4.2 is merged, PR #20).

## What M4.3 is, and isn't

M4.2 is everything you can draw on a board. M4.3 is the rules around it, and getting a level to someone else.

| In M4.3 | Not in M4.3 |
|---|---|
| **Rules tab:** objectives, limits (`max_lines`, `max_numbers`, comments, required and banned constructs), par, starter code | Difficulty and tier tags, free play (M4.4) |
| **Hints tab:** up to three tiers, written by the author | "Save to the repo" for the designer (see question 4: it moves to M4.4) |
| **Other boards** (variants): a board switcher, each board its own tiles, text, start, goal, enemies | A server, accounts, a public gallery |
| **Solvability check:** the shortest search moves into the engine; counts only, per board | Judging levels with code clocks, or proving a level can be solved by *any* program |
| **The author's solution:** kept from a solved test-play | Notes on why a solution is written as it is |
| **Sharing:** a link, a code, a `.yaml`; opening one; "Shared with me"; remix | Names, avatars, ratings, "send to the designer" |
| Test-play now shows hints, par and the solution offer, as a player would see them | Sound for the editor (painting stays silent) |

## What I measured first

Both numbers shaped the design, so they're here. (Counts and times only; no level or route was printed.)

- **The search can't be one blocking request.** The 109 boards in the repo's levels all solve in 0.15 s or less in
  native Python. But an author's board is bigger and freer: a 12×12 board with **6 gems took 3 s, 8 gems 16 s, and 6
  gems plus one patrol about a minute**. Pyodide is several times slower than that. The worker's watchdog is 3 s and
  terminates the worker (which resets the scratch REPL). So the search runs in short slices with progress and a Cancel
  button, and a cap on how many positions it will look at (see 3).
- **A share code is small.** Every level in the repo, hints included, is 2.7 KB at most as JSON, 742 bytes deflated and
  992 characters as base64url (median 728). With an author's solution added, expect under 1.5 KB: a link that fits in
  any chat message.
- **Repo maxima, for the size limits** (a shared level is capped by the same table as every level): title 21
  characters, brief 286, trains 107, a hint 233 (3 hints at most), a sign/rune/question/answer 101, 4 boards, 5
  enemies.

## Decisions to confirm

Each has a recommendation; the first is what I'll build unless you say otherwise.

### 1. The Rules and Hints tabs

The properties panel has Level / Square / Enemy. It gains **Rules** and **Hints**, five short tabs. (Share is a
dialog, not a tab: it's an action, not a property.) Every control edits the same level file keys the repo's levels
use (`objectives`, `constraints`, `par`, `hints`, `starter`), as views over `draft.extra`, so a key the tab doesn't
recognise is kept exactly as it was. All wording the player will read comes from the engine (`Level.goals`, `rules`,
`stars`), shown under the controls as **"What the player will read"** once the engine accepts the draft, so the author
never writes a rule's sentence.

**Rules tab, three groups:**
- **The goal.**
  - Reach the goal (on by default).
  - Say a phrase: a list of phrases, add and remove.
  - Collect gems: off, all, or at least *n*.
  - Capture enemies: off, all, or at least *n*.
  - A note that waypoints on the board are always required (the engine adds them).
  - A level the controls make impossible (collect gems with no gems on the board) is not blocked: the engine's problem
    appears on the **Rules** tab and the Problems list, like any other.
- **Limits.**
  - Most lines of code; most numbers (1 means "one number, written once"); comments required.
  - **Required** and **banned** constructs, each a checklist of Python's names for them ("a `for` loop", "an `if`",
    "an f-string"…). The list comes from the engine (`editorOptions.constructs`, node name and label), so the
    editor holds no list of its own, and a pytest checks every entry is a real `ast` node.
- **Par and starter code.** Par: lines of code to earn the second star. If a solution is kept, a button
  **"Use my solution's *n* lines"**. Starter code: what the player's editor starts with (optional).

**Hints tab.** Three fields: **1. A nudge**, **2. How it works, in words**, **3. Show the code**, with a line saying
what each tier is for (the shape from `hint-tiers`). Tiers fill in order (an empty one trims the ones after it).
Plain text; `` `backticks` `` become code, as in the curriculum. Opening the first hint costs the third star, and the
tab says so.

**Spoilers:** copying a lesson level still never copies its hints or starter (M4.2), so the Hints tab starts empty on a
copy. A copy keeps the level's objectives, constraints and par (the Challenge panel already shows all three).

### 2. Other boards: a board switcher over the same editor

A level can run on several boards that one program must solve (`variants`). The editor treats them as first-class:

```
┌ toolbar … ──────────────────────────────────────────────────────────┐
│ Boards:  [ Board 1 ] [ Board 2 ] [ + Add a board ]   (Remove this board)  │
│  palette │         the board being edited            │ properties    │
```

- **Level-wide** (edited once, whichever board you're on): title, brief, abilities, facing, planks, objectives,
  limits, par, hints.
- **Per board:** size, tiles, the text on signs, runes and gates (a guard can ask the same question with another
  answer on each board, which is the whole point of boards), start, goal, enemies.
- **Add a board** copies the board you're on, so you edit only what differs. Up to 6 boards (the repo's most is 4).
  **Remove** asks first. Switching board keeps the undo history (one history for the level).
- A level has `?` squares **or** other boards, never both. The editor allows the state and the engine's problem says
  so, ringing the Boards row.
- **How, with little churn.** The draft keeps its main board in the fields it has today and gains `boards`: the other
  boards. `viewOf(draft, i)` gives a draft whose main fields are board *i*'s, `commit(draft, i, edited)` puts them
  back. Every editing function, the board and `draftToLevelInfo` keep working on the view, unchanged.
- **Export** assigns legend symbols across all boards together (the same details share a symbol, different details
  get another), so the repo's per-board legend overrides aren't needed; a board with no enemies gets `enemies: []`
  written out when board 1 has some (absent means "same enemies"). This replaces M4.2's "symbols the variants use are
  never reused" workaround.
- **The engine's `at` gains `board`** (1-based; absent means board 1), so a problem on board 2's square rings the right
  square and switches to the right board.
- **Risk, and the guard.** This is the one change to M4.2's model. `roundtrip.test.ts` already sends every repo level
  through a draft and the real engine and compares what the engine describes; 22 of the repo's 45 levels have other
  boards, so the guard is in place before I change anything. If it ever bites, the fallback is the M4.2 behaviour
  (other boards kept raw, shown but not editable).

### 3. The solvability check

A button in the Problems section: **"Can it be solved?"**. It is for the author who has drawn a board and wants to know
whether a route exists, and roughly how long.

- **What it searches** is what `scripts/solve.py` searches today, played on the real engine: moving, turning, waiting,
  capturing, bridging, and saying a phrase the level knows. It does **not** read runes, use `look()`, count or loop,
  so it can't judge *programs*.
- **Per board** (and per place a hidden goal could be). It can say, for each:
  - *"A route exists: plain calls do it in 6 lines. A loop might do it in fewer."* The number is **not** a par
    suggestion; it's an upper bound.
  - *"No route found."* Every move, turn, wait, capture and bridge was tried: the goal can't be reached.
  - *"Gave up after 200,000 positions."* **Different from "no route"** (today's `fewest_lines` returns `None` for
    both, so the engine's version keeps them apart). It might be solvable; try fewer gems or enemies.
  - *"Can't judge: obstacles tick with your code's lines."* (`clock: line` and `new_line`.)
- With several boards it says so plainly: *"Each board can be solved on its own. That doesn't show one program can
  solve them all: your solution, from test-play, does."*
- **It never shows the route, the moves or the code.** Counts and words only. The curriculum rule stands: the editor and
  the solver never show a curriculum level's hints, references or notes; on a copied lesson level it says what it says
  on any level.
- **How it runs: in slices.** `rankfile/search.py` holds the search from `scripts/solve.py` as a resumable `Search`;
  two requests, `solveStart` (the level) and `solveStep` (about 150 ms of work, then progress), so no single request
  nears the 3 s watchdog and **no watchdog change is needed**. Between slices the editor's other requests (the
  debounced checker) run, so painting stays live. Cancel stops asking. Changing the draft cancels the search and marks
  its answer "for an older draft". The cap (200,000 positions per board, to be measured in Pyodide) lives in the
  engine.
- `scripts/solve.py` stays as the command-line tool; it imports `search.py`, and `write_code` stays in the script (only
  the generators use it). The generators must still write identical files: I'll rerun them and compare sha256, as the
  rules say.

### 4. The author's solution

- **A new optional level key, `solution`** (the author's code, as text, at most 2,000 characters). The engine checks it
  is text and within the limit; `describe()` never includes it. A test makes sure **no repo level has a `solution`
  key** (reference solutions stay in `solutions/`, out of the bundle, which `check:bundle` guards).
- **It is written in one way only:** a solved test-play shows **"Keep this as the level's solution"** on its outcome
  card, which stores the code in the draft. The Rules tab shows "Solution kept: *n* lines" and a Remove button.
- **The proof is the engine's.** When you press Share, the editor runs your kept solution on the current draft
  (`runLevel`, with no hints). Only `solved` passes: it must solve **every** board, and keep the limits. So an edit that
  breaks your solution is caught: *"Your solution no longer solves this level (board 2: …). Test-play it again."*
- **Par must be reachable.** If par asks for fewer lines than the kept solution uses, sharing is blocked with the
  reason and a one-click **"Set par to *n*"** (see question 7).
- **A carried solution is never run by the person who receives it** (see Safety). It is shown as text, after three
  failed runs, in the comparison dialog titled "The author's solution".

### 5. Sharing, without a server

- **Three ways out,** from a **Share…** dialog (toolbar, next to Export):
  - a **link**, `…/#/play/<code>`;
  - a **code**, the same text, for pasting into My levels → **Open a link or code** (a long link can get cut off in
    chat);
  - a **`.yaml` file**, the export, for the repo or for backup.
- **The code** is `rf1.` then base64url of the level (JSON, with its `solution`) compressed with the browser's own
  `CompressionStream` (deflate), so no dependency. The `rf1` is a version, so a later format can be told apart.
- **The dialog says what travels:** *"the title, boards, rules, hints and your solution. Nothing else: no name, nothing
  from your browser."* It also says the part of a link after `#` is never sent to a server. It lists what's blocking
  (a problem the engine reports, no kept solution, a solution that no longer solves it, par out of reach) and the
  buttons stay disabled until none is left.
- **Opening a link or code** (`#/play/<code>`, or pasted into My levels): decode, check, show the real level screen
  (`mountLevel` with a `shared` option): the Challenge tab with goals, rules and the author's hints, no lesson. The
  crumb is *Shared level / title*. If the code is damaged or too big, or the engine refuses the level, a plain page
  says why, and goes back. A refused level doesn't open for play.
- **"Shared with me"** (see question 5): every level you open is kept, by content, in a section of the My levels page:
  title, your stars, Open, Remix, Remove. M4.4 moves it into Free Play.
- **Remix** ("Open in the editor" on a shared level, and in the list) makes a draft of your own: a new id, the author's
  title with "(remix)", **without the author's solution** (you're changing it; prove your own).
- **Progress** on a shared level is kept in its own store, keyed by the level's content (`shared-` and the first 12
  characters of a SHA-256 of the level without its id), so opening the same link twice finds your stars and hints, and
  two copies of one level never split. It never earns a crown, a promotion or a "next level". The stars work as in the
  curriculum (solved, par, no hints).
- **Test-play** is the same screen with a throwaway, in-memory progress store, so the author sees exactly what a player
  will (hints one at a time, par, the solution offer after three failed runs) and nothing is saved.

### 6. Safety: what arrives is data, and is never run

A link can come from anyone, so:

1. **Size.** The code is capped (20,000 characters); decompression is read in chunks and **aborted past 64 KB**, so a
   compression bomb can't fill memory. A `.yaml` file keeps M4.2's 64 KB cap.
2. **The engine checks it,** through `loadLevel`, as everything else (unknown keys refused, 12×12, six boards). A table
   of limits in `levels.py` caps every free-text field, for repo and shared levels alike (title 60, brief 600, trains
   200, five hints of 600, text on a square or a phrase to say 300, 12 enemies, starter and solution 2,000), set well above the repo's maxima, with a
   test that every repo level fits.
3. **Text stays text.** Everything is drawn with `h()` text nodes, and `` `code` `` spans through `withCode`. A shared
   level has no Markdown lesson and no solution note, so it never reaches the two places that insert HTML
   (`lesson.ts`, `compare.ts`'s note). The author's solution is shown in a read-only editor.
4. **A shared level's id is rewritten** to `shared-<hash>`. The app looks things up by id (progress, the curriculum's
   reference solutions through `loadSolution`, the Codex); a shared level named `ch01-l01` would otherwise read someone
   else's progress or open **the curriculum's reference solution**.
5. **Someone else's code is never run on your machine.** Pyodide in a worker can reach the network (`import js`;
   "Known trade-offs" in ARCHITECTURE.md), and that is fine for code you write yourself, but not for a stranger's. So:
   a carried `solution` is displayed, never executed; Import (file or link) and Remix **drop it**; and the editor
   writes a `solution` only from your own solved test-play. The price: importing your own exported file loses its
   solution, and you re-prove it with one solved test-play.
6. **Nothing is sent anywhere.** Opening a link is a local decode; the fragment is not part of the request.

## The model, briefly

```ts
interface Draft {
  …M4.2's fields (the main board: width, height, cells, start, goal, spots, enemies)…
  boards: DraftBoard[];            // the other boards (none for most levels)
  extra: Record<string, unknown>;  // objectives, constraints, par, hints, starter, solution… as views, see rules.ts
}
type DraftBoard = { width; height; cells; start; goal; enemies };
```

New modules: `src/editor/rules.ts` (objectives, constraints, par, hints, starter, solution as views over `extra`),
`boards.ts` (`viewOf`, `commit`, add, remove), `solve.ts` (drives the slices); `src/share/codec.ts` (encode, decode,
caps, the content hash), `src/share/shared.ts` ("Shared with me" and its progress store); screens `ui/editorRules.ts`,
`ui/shareDialog.ts`; the route `#/play/<code>` in `app.ts`. In the engine: `rankfile/search.py`, the limits table, the
`solution` key, `editorOptions.constructs`, `at.board`; `protocol.ts`, `worker.ts` and `bridge.py` get `solveStart` and
`solveStep` together.

Existing code that generalises: `ProgressStore` takes its storage key (and can be in-memory); `HelpPanel` takes a
progress store and a solution loader instead of the curriculum's; `openComparison` takes that loader and a title. Both
default to what they do today, so the curriculum doesn't change.

### Decided without the designer (2026-10-22)

Small choices the spec left open, decided as recommended; the designer can overturn any of them at the PR.

1. **The solution's line count comes from the engine.** A new request `codeLines` (`bridge.code_lines`, the same count
   par and `max_lines` use) gives "Kept: *n* lines" and "Use my solution's *n* lines"; the editor never counts lines.
2. **"Open in the editor"** on a shared level's banner is Remix: a new draft of your own, without the author's solution.
3. **The share code holds the level with its id;** the receiver rewrites the id to `shared-` and 12 hex characters of a
   SHA-256 of the level's JSON with its keys sorted and its id left out, so the same level always lands on one id.
4. **A link or code is accepted pasted whole or bare:** anything after the last `#/play/` is the code.
5. **Shared levels are kept under `rank-and-file:shared`, their progress under `rank-and-file:shared-progress`;**
   `ProgressStore` takes the key, and only the curriculum's store remembers ceremonies and crowns.
6. **Import (file or code) and Remix drop a carried `solution`;** the Share dialog's checks run the author's own kept
   solution, which only their solved test-play wrote.
