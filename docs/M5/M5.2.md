# M5.2 · Chapter 7, Spellbook: spec

**Status: approved *(Designer, 2026-11-18: "approved, all nine as recommended")*: gate 1 passed. Building.
The design sheet is whole (`/design/spellbook.html`) and waits for the designer's picks.** Branch: `m5-2-chapter-7`.

M5.2 is the Knight tier's first chapter: six core levels and an optional mastery challenge that teach functions
(`def`, parameters and default values, `return`, scope), played as the knight. It builds on `docs/M5/M5.md`
(decisions 5 to 7 and the Chapter 7 outline, all *(Designer, 2026-11-17)*) and on the knight of M5.1.

*(Recommended)* marks a recommendation that waits for the designer's answer. Levels are described by what they
train and their board mechanic, never by how to solve them.

## What the investigation found *(M5.2-0, an Opus lead, read-only, 2026-11-18)*

Everything below was run on the real engine, not read off the code.

**Two faults that are already in the published game.** No lesson so far asks for a function, so nobody has met
them; Chapter 7 would on its first level. Both are fixed in M5.2 (packages 1 and 2a).

- **What a line does after a function hands back is lost from the recording.** In `knight.jump(side(), 2)` the
  knight really jumps, but playback never shows it; `print(double(3))` prints, but the console never shows the
  line; a name set from a function's answer on the last line never reaches the variables panel.
- **The scope mistake 7.5 is built around gets a broken message:** "Python doesn't know the name ``", with the
  name missing.

**What already works:**

- **Stepping into a function.** The `def` line is a step, each call is a step, and every line of the body is a
  step on every call. Each step already says which function it is in; the UI has never used it.
- **Too few or too many arguments** already get kind messages ("`hop()` needs more inside its parentheses: a
  value for `b`").
- **A function that calls itself forever** ends with "A function kept calling itself and never stopped, so Python
  gave up." (Not yet tried in the browser's Python: one e2e check.)
- **Line counting:** a `def` line counts as one line, for limits and for par. The clockwork that ticks "the first
  time each line runs" ticks a function's body on its first call only.
- **The editor and `show_level`** pass an unknown key of a level through, so the examiner's field needs no editor
  work before M5.5.

**What is missing:**

- **Inside a function the variables panel shows only the function's own names:** the program's names, and the
  knight, vanish until it ends. Functions themselves are listed among the program's names ("function hop").
- **After a function ends the highlight never goes back to the line that called it** (the first fault above).
- **No friendly words** for: a name that only exists inside a function, a call above its `def`, or using the
  `None` that a function with no `return` hands back.
- **A rule cannot name a function** today, nor count its parameters, its calls or its defaults, nor ask for a
  `return` with a value.
- **The Codex has no entries for keywords at all** (not for `for`, `while` or `if` either): its entries are
  abilities, properties, built-ins and text methods. `help("def")` prints seven thousand characters of Python's
  own reference manual.
- **`help()` on the player's own function** gives Python's raw text ("Help on function stride in module
  __main__").
- **The row of boards above the board** marks a tick on each board's goal square; with one call per board it
  needs the call's text and its answer instead.

A prototype of the examiner worked on the first try: the engine runs the player's program, finds the function,
checks it takes the arguments, and calls it under the same recorder, so the call's lines, its output and its
errors all land where playback expects them.

The options stay below as the record of what wasn't chosen.

### 1. How the boards keep the knight's geometry out of the puzzle

Pedagogy rule 16: working out a knight's route by eye is a chess puzzle, not a Python one. On an open board the
player would spend the level finding a route. Chapter 7's boards need the route to be plain to see, so what is
left is the code.

- **A. Stepping stones over a chasm** *(Recommended)*: the squares the knight may land on are floor "stones"; the
  rest of the board is pits. The route is the stones. A figure that repeats on the board is a function waiting
  to be written, and the player can see it before writing a line. A wrong jump is a fall (a lost run), and the
  landing rings and the pits' own marks already say so.
- B. Stones between walls: the same, with walls instead of pits. A wrong jump is an error at that line instead of
  a fall, and the landing rings then show *only* the next stones, which nearly plays the level for you.
- C. Open boards with the squares to visit marked by gems or waypoints. Less stark, but shorter routes that skip
  the pattern would be allowed, and judging them is the chess puzzle again.

Both A and B go on the design sheet as drawn boards; walls still appear on A's boards where a level wants a jump
over something. Whichever is picked, the generator checks (counts only) that no shorter route skips the stones.

### 2. Where the examiner comes in

M5 decision 6 brought the examiner into Chapter 7; the outline put its first appearance in 7.4 (`return`).
Designing the levels suggests it should arrive one level earlier.

- **A. In 7.3, giving orders; in 7.4, wanting answers** *(Recommended)*:
  - 7.3: the examiner calls your function on several boards with a different size each time, and once with no
    size at all. The knight has to finish on the goal. A parameter is the only way to pass, and so is a default:
    nothing is forced by a rule.
  - 7.4: the same examiner now wants something handed back. `return` is the only new thing in that level.
  - One new thing per level: 7.3 brings the examiner (you write no calls, so there is less to write, not more);
    7.4 brings `return`.
- B. As outlined: 7.3 is driven by the player's own program on one board (the same manoeuvre called at three
  sizes, forced by a line limit, and the default value forced by a rule); the examiner first appears in 7.4
  together with `return`. Two new things land in 7.4, and 7.3's default value is there because a rule says so.

### 3. What the examiner shows, and when

- **A. The calls before the run; what it wanted and what came back after** *(Recommended)*: the Challenge panel
  lists every call the examiner will make (`fetch(3)` on board 1, …), next to the boards. After a run each call
  shows a tick or a cross, and for an answer: "wanted 7, got None". It is the first taste of a test report
  (Chapter 16), and "got None" is the best teacher of print-versus-return there is.
- B. The wanted answers before the run too, as real tests show them. Nothing to work out by eye, but on boards
  where the answer is written on a rune it gives nothing away either. Slightly more to read before starting.
- C. Never the wanted answer, only right or wrong, as the gate guards do. Keeps a secret that isn't one.

Two things follow whichever is picked *(Recommended)*:
- **Every call gets a fresh board.** One call, one board, one replay, as several boards work today. (Calls that
  carry on from each other on one board can be added later if a level wants them.)
- **The answer has to be the right kind of thing.** The number 7 is not the text "7", and the examiner says which
  it got ("gave back '7', which is text"). Chapter 6 taught the difference; this is where it pays.

### 4. Your own code on an examiner level

On an examiner level the player's job is to *define*; the examiner makes the calls. A player will naturally add a
call of their own at the bottom "to try it".

- **A. A rule stops the run before it starts** *(Recommended)*: "On this level the examiner makes the calls: take
  out line 9." The program may hold `def`s and nothing that acts. Trying it is what Run is for: every call is
  played back on its board.
- B. The program runs as written, then the examiner calls. Honest Python, but a try-out call left in moves the
  knight before the examiner starts, and the failure that follows is hard to read.

### 5. The examiner's voice

The gate guards have a voice ("Do you not know how to count!?"). *(Recommended)* The examiner gets one too:
short, pedantic, fair. A line when a call passes, one when it fails, one for "you printed it, you didn't hand it
to me". The lines are written with the levels and shown at QA1; the design sheet shows where they appear.

### 6. The guard in 7.5 hears a knight the way guards hear a pawn

A guard hears only a piece standing right beside its gate, and a knight can never jump from that square straight
onto the gate. *(Recommended)* Keep the rule: on 7.5 the path passes the stone beside the gate, the knight
answers there, and the gate itself is a stone a few jumps further along the same path. It is plain on a
stepping-stone board, and no engine rule changes. Not chosen: letting guards hear a knight from a jump away (a
second rule to learn, for one level).

### 7. Keywords in the Codex

The M5 plan lists Codex entries for `def`, `return` and parameters. The investigation found the Codex has never
held a keyword: `for`, `while` and `if` have no entries either.

- **A. A "Keywords" section, with the earlier ones filled in too** *(Recommended)*: `def` (with parameters and
  default values inside its entry) and `return` from Chapter 7, and `for`, `while`, `if`/`elif`/`else`, `break`
  and `continue` from the Pawn tier, each appearing when its lesson has been read. `help("def")` answers with the
  entry instead of the reference manual. The mechanism is built once; the older entries are a few more short
  texts, written by the orchestrator and read by the designer at QA1.
- B. `def` and `return` only. Cheaper by those texts, but the section would hold two entries and a player would
  fairly ask where `for` is.
- C. No keyword entries: the Codex stays "a dictionary of the functions you know".

Either way `help()` on the player's own function gives its first line and its docstring in the Codex's plain
style, without "in module __main__".

### 8. Does a docstring cost a line?

Today a docstring would count against a line limit and against par, so labelling a function could cost a star.
*(Recommended)* It counts for nothing, exactly like a comment. Not chosen: leaving it as it is.

### 9. Titles and copy

*(Recommended, as a set)*
- Chapter 7 is **Spellbook**; its summary in the level list: "Functions: spells of your own that take orders,
  hand back answers and cast each other, and a knight to cast them."
- Level titles as below. The examiner calls the player's function by a name the level gives (the Challenge panel
  shows it); on every other level the player picks their own names.
- The promotion screen's teaser loses "Its levels aren't built yet": "The knight moves in an L, over anything in
  its way. Chapter 7 is waiting."

## The levels

One chapter, seven levels. On every board `P` is the start and `G` the goal. A **stone** is a floor square in a
field of pits (decision 1). A **stride** below means any short figure of jumps that repeats; which jumps make it
is the player's to read off the board. Every level's abilities include `jump`; nothing else unless listed.

What each level trains, and what makes it necessary:

| Level | Trains | What makes it necessary |
|---|---|---|
| 7.1 Stepping Stones | `knight.jump(dx, dy)` | It is the only way the knight moves |
| 7.2 A Spell of Your Own | `def`, and calling it | One figure of jumps comes up three times, joined by jumps that differ, so no loop covers it; written out, the route is over the line limit |
| 7.3 Spells That Take Orders | parameters, a default value | The examiner calls it with a different size on every board, and once with none |
| 7.4 Spells That Answer | `return` | The examiner wants a number that is written at the far end of each board, and differs on every one |
| 7.5 What Happens in the Spell | scope | A total has to be built from several calls of one function; the obvious way (changing an outside name from inside) is exactly what Python refuses |
| 7.6 Spells That Cast Spells | functions calling functions | A long route made of figures inside figures; one layer of functions is still over the line limit |
| 7.7 The Examiner's Round *(mastery, optional)* | all of it, to par | The examiner runs one behaviour on several boards |

### 7.1 · Stepping Stones

- **Trains:** the jump: `knight.jump(dx, dy)`, what the two numbers mean, that it passes over anything and takes
  what it lands on.
- **Brief:** "Your pawn is a knight now. It can't walk a single square, and no wall can stop it. Cross the
  stones."
- **Board:** one board, about 9 by 5. A path of stones over the chasm, a wall across the middle that the path
  jumps over, and an enemy standing on one stone of the path. The path repeats one pair of jumps several times,
  so a `for` from Chapter 3 earns the par star.
- **Goals:** end on the goal; take the enemy. **Rules:** none. **Par:** the route with its repeat in a loop.
- **Must fail:** a `move()` ("Knights don't walk: they jump"); a jump that isn't an L; a landing in the chasm.
- **Lesson** (on its own small board): a jump over a wall and one onto an enemy; a `run error` snippet with a
  jump that isn't an L; a `run lost` snippet landing in a pit.

### 7.2 · A Spell of Your Own

- **Trains:** `def`: naming some lines, the indented body, calling it by name; that defining is not running; that
  a function has to be defined before it is called.
- **Brief:** "The same steps, again and again, with something different in between each time. Teach your knight
  the steps once, and give them a name."
- **Board:** one board, about 10 by 8. The path is one figure of four jumps, three times over, joined by single
  jumps that are not the same. The repeat is visible in the stones.
- **Rules:** a line limit the written-out route does not fit and the function does; the code defines a function
  and calls it. **Par:** the line limit.
- **Must fail:** the route written out (too many lines); a `def` that is never called (the knight never moves,
  and a note says the function was never called); a call above its `def` (an error).
- **Lesson:** a `def` and two calls; a `def` alone, which does nothing; a `run error` snippet calling the
  function above its definition.

### 7.3 · Spells That Take Orders

- **Trains:** parameters: a function with blanks, arguments filling them in order; a default value for a blank
  nobody fills.
- **Brief:** "The examiner will call your spell `gallop`: which way, and how many strides. Sometimes it won't say
  how many. Then it means one."
- **The examiner calls** `gallop(direction, strides)` on four boards: a different number of strides on each, east
  on some and west on others, and on one board with the direction only.
- **Boards:** four, each a single row of stones as long as its call needs, the knight starting at one end and the
  goal on the last stone. The boards and the calls are shown before the run.
- **Rules:** the program only defines (decision 4). **Par:** the spell at its shortest.
- **Must fail:** a spell with the size typed inside it (right on one board only); a spell with no default (the
  call that gives no size: "it was called with 1 value and needs 2"); the two parameters swapped.
- **Lesson:** a function with one parameter, called at two sizes; a second parameter with a default; a
  `run error` snippet leaving out an argument. One snippet is an examiner at work on the lesson's board
  (pedagogy rule 12: a new interaction is shown in its lesson).

### 7.4 · Spells That Answer

- **Trains:** `return`: handing a value back to whoever called; the difference between printing a value and
  returning it; a function with no `return` hands back `None`.
- **Brief:** "At the far end of the stones is a rune with a number on it. The examiner sends your knight for it,
  and wants the number back."
- **The examiner calls** `fetch(strides)` on four boards and checks two things: the knight ends on the far
  stone, and the function hands back the number written there, as a number.
- **Boards:** four rows of stones of different lengths; the last stone of each is a rune with its own number
  (one of them two digits long).
- **Abilities:** `jump`, `read`. **Rules:** the program only defines. **Par:** the spell at its shortest.
- **Must fail:** printing the number instead of returning it ("wanted 7, got None", and the examiner's line about
  it); returning the rune's text instead of a number (Chapter 6's `int()`); one board's number typed in;
  returning before the knight has moved.
- **Lesson:** a function that returns, and its result used twice; the same function printing instead, and the
  `None` that comes back; "`return` also ends the function right there" in a sentence. The knight reading a
  rune it has landed on appears in a snippet (the ability is the pawn's, the landing is new).

### 7.5 · What Happens in the Spell

- **Trains:** scope: a name made inside a function lives only there and starts fresh on every call; a function
  can read the program's names but an assignment inside makes a new name of its own; so values go in through
  parameters and come out through `return`.
- **Brief:** "Three toll bridges. Every stone on a bridge names its toll. At the gate the guard asks what the
  three crossings cost you in all."
- **Board:** driven by the player's own program, on three boards. The path crosses three rows of rune stones of
  different lengths (each rune a number, different on every board), joined by plain stones. It then passes the
  stone beside a guard's gate; the gate is a stone further along, with the goal beyond it (decision 6).
- **Abilities:** `jump`, `read`. **Rules:** a line limit that three written-out loops do not fit; the code
  defines a function and calls it. **Par:** the line limit, or one under.
- **Must fail:** one board's total typed in; a total kept outside the function and added to from inside it (an
  error, with a friendly explanation: this is the mistake the level exists for); a function that prints its
  sum instead of returning it; using one of the function's own names after it has ended (an error).
- **Lesson:** a function's own name used outside it (`run error`); a counter outside the function changed from
  inside (`run error`); the same job done right, returning and adding up outside. The variables panel shows
  the two sets of names apart while each snippet plays.

### 7.6 · Spells That Cast Spells

- **Trains:** a function calling another function; taking a long job apart into small named pieces; a docstring
  as a label (the lesson's aside).
- **Brief:** "The longest road yet, and the shortest spellbook you can write for it. Small spells, and bigger
  spells made of them."
- **Board:** one board, up to 12 by 12, driven by the player's own program. A long path of stones built from a
  small figure, which sits inside two bigger figures, which are joined by jumps that differ. The figures are
  visible in the stones.
- **Rules:** a line limit. **Par:** the line limit, or a little under.
- **Must fail** (the generator checks each by count): the route written out; loops only; functions that never
  call each other. Each is over the line limit.
- **Lesson:** a function that calls another; a docstring, and `help()` on the player's own function showing it.

### 7.7 · The Examiner's Round *(mastery, optional)*

- **Practises:** everything in the chapter, to par. It teaches nothing new (pedagogy rule 15): `def` (7.2),
  parameters and a default (7.3), `return` (7.4), names kept inside a function (7.5), a function calling
  another (7.6), `read()` and `int()` (Chapter 6), `for` (Chapter 3).
- **Brief:** "The examiner's last test: several toll bridges in one ride, and it wants the whole bill."
- **The examiner calls** one function on four boards with the number of bridges and the stones on each (once
  leaving the second out). The knight has to finish on the goal and the function hands back the total toll.
- **Boards:** four, each with as many toll bridges as its call says, joined the same way every time.
- **Abilities:** `jump`, `read`. **Rules:** the program only defines. **Par:** tight: it wants a helper function
  and no wasted line.
- **Must fail:** one board's answer typed in; a spell with the sizes typed inside it; a spell with no default.

**Pars and line limits are provisional** until the references are written blind. The generator's probe (counts
only) confirms every "must fail" and "what makes it necessary" above before QA1, and what it finds is recorded
in "As built".

## Level content *(the orchestrator's, written blind)*

A new generator, `scripts/gen_spellbook.py`, writes `levels/ch07/`, `solutions/ch07/` (a reference, the wrong
attempts and a note for each level) and `lessons/ch07/`, and prints only counts. It lays the stones from figures

real engine, and checks that no shorter route skips the stones. Hints follow the three tiers (a nudge; the
mechanic in words; its code). `docs/Codex.md` gains the chapter's entries.

## The Codex's keywords: the words *(decision 7; for package M5.2-7, read by the designer at QA1)*

A keyword's entry says how it is written, what it does, and shows a short example; like every entry it names the
level that brought it in, and appears once that level's lesson has been read. The Codex tab lists them under
"Keywords". None of the examples is on a board, so none is a hint for a level.

| Keyword | How it is written | What the entry says | Example |
|---|---|---|---|
| `for` | `for name in things:` | Run the indented lines once for each item, with `name` holding that item. `range(3)` hands out 0, 1 and 2. | `for i in range(3):`<br>`    print(i)` |
| `if` | `if condition:` … `elif other:` … `else:` | Run the indented lines only if the condition is true. `elif` tries another condition when the ones above it were false; `else` runs when none were true. Both are optional. | `if steps > 3:`<br>`    print("far")`<br>`elif steps == 3:`<br>`    print("just right")`<br>`else:`<br>`    print("near")` |
| `while` | `while condition:` | Run the indented lines again and again, for as long as the condition is true. It is checked before every lap, so something inside has to change it. | `left = 3`<br>`while left > 0:`<br>`    left = left - 1` |

## The examiner's words *(decision 5; for package M5.2-4b-2, read by the designer at QA1)*

A case's summary is two parts: **what happened**, in plain words, then **the examiner's line**, in quotes. The
engine keeps the two apart (so the pick S1 to S3 can put the line where it belongs) and joins them with a space
for the summary. The names and values below are made up; a value is shown as Python shows it (`7`, `'7'`), a
kind of value in the words the error messages already use ("a whole number (an int)", "text (a str)").

| When | What happened | The examiner's line |
|---|---|---|
| The call passed, no answer wanted | The examiner called `gallop(1, 3)`, and the board is as it should be. | “Correct. I had rather hoped to be disappointed.” |
| The call passed, with an answer | The examiner called `count(4)`: it wanted 7 and got 7. | the same |
| No such function | The examiner called `gallop(1, 3)`, and your program has no function called `gallop`. Define it with `def gallop(...):`. | “I called. Nobody answered to that name.” |
| …and one of yours is a near miss | The examiner called `gallop(1, 3)`, and your program has no function called `gallop`. It has `gallup`: the examiner needs the name letter for letter. | the same |
| The name isn't a function | The examiner called `gallop(1, 3)`, but `gallop` in your program is 3, a whole number (an int), not a function. Keep that name for the `def`. | “I can call a function. I cannot call that.” |
| The wrong number of values | The examiner called `gallop(1, 3)` with 2 values, and your `gallop` takes 1. Each value needs a name inside the parentheses of its `def` line. | “I hand over what the task says: no more, no fewer.” |
| | (how many it takes: "none", "1", "none or 1", "1 or 2", "up to 3", "from 1 to 3", "1 or more"; "with 1 value", "with no values") | |
| It printed its answer (a printed line is the answer wanted) and handed back nothing | The examiner called `count(4)` and got nothing back (None); it wanted 7. Your function printed its answer, but the examiner doesn't read the screen: `print` shows a value, `return` hands it back. | “You showed me the answer. I asked you to hand it to me.” |
| It handed back nothing | The examiner called `count(4)` and got nothing back (None); it wanted 7. A function hands a value back only with `return`: check that every way through `count` reaches one. | “I held out my hand, and nothing was put in it.” |
| The wrong value | The examiner called `count(4)`: it wanted 7 and got 8. | “An answer, certainly. Not the answer.” |

## How it is built

**The contract, committed before any package** (names only; an Opus lead writes it as stubs and types).

- **A level's examiner** is a new key of the level file, so levels stay data:
  ```yaml
  examine:
    function: gallop
    calls:
      - {args: [1, 3], board: 1}            # board 1 is the map, 2 the first of `variants`, …
      - {args: [-1], board: 2, returns: 4}  # `returns` is optional: left out, only the board is judged
  ```
  Arguments are plain values, given in order; a call with fewer values is how a default is exercised. The level's
  `objectives` judge each call's board. The checker refuses an examiner together with `?` squares, a board no
  call uses, a call to a board that isn't there, and more calls than a level may have boards.
- **Engine:** `Level.examine`; `Level.cases()` gives one case per call, labelled with the call's text;
  `runner.execute(..., call=...)` runs the program, then finds the function, checks it takes the arguments and
  calls it under the same tracer; the result gains `call`: the call's text, what came back, what was wanted, and
  the step where the call starts. A case is judged in this order: an error, a lost run, a problem with the
  function itself, the answer, the board. `describe()` lists the calls and never the wanted answers (decision 3).
- **What the examiner can say** (the words are settled with the levels): the function isn't defined (with a "did
  you mean" for a near miss); the name isn't a function; it takes the wrong number of values; it printed its
  answer and handed back nothing; it handed back nothing at all; the wrong value; the right value as the wrong
  kind of thing; the board's goals not met after the call.
- **Rules a level can set,** checked with `ast`:
  ```yaml
  constraints:
    functions: {gallop: {params: 2, defaults: 1, calls: 2, returns: true}}   # every key optional
    define: 1          # at least this many functions of the player's own naming, each called
  ```
  An examiner level adds, by itself, "the program only defines" (decision 4) and "define a function called …".
  A docstring stops counting as a line (decision 8).
- **Steps:** a step inside a function carries the program's names as well as the function's own (`globals`), and
  how deep the call is. When a function ends, a step is opened for the rest of the calling line, so what that
  line goes on to do is recorded and the highlight returns to it. It is not counted as another line run and
  ticks no clock.
- **Lessons:** a snippet can be marked as one the examiner calls (```` ```python run calls gallop(1, 2) ````), and
  the call travels the lesson's path to the engine.
- **The Codex:** a new kind of entry, `keyword`, unlocked by the constructs a lesson's snippets use.
- `protocol.ts` mirrors all of it.

**Names:** the examiner's functions are never named like a Python built-in (`sum`, `max`, `next`…): the level
checker would take a call to one for the built-in.
